Optimistic UI

Conflict Resolution

Conflict resolution starts with business rules, not algorithms.

Sync conflicts: not as simple as it seems

Device A and device B both edit the same entity offline. When they reconnect, the backend receives two versions, and one of them was based on outdated data. What should win?

The simple approach

Last Write Wins

  • The value can be safely replaced
  • Settings
  • Colors
  • “Last seen” time

First Write Wins

  • First accepted claim wins
  • Task ownership
  • Seat reservation
  • Code redemption

Choosing between them is a product decision: what does the user expect to happen?

Merging changes, and how it goes wrong

A smarter approach merges field by field: take the fields each device changed and combine them. It sounds safe until two independent edits combine into something invalid.

// Original
{ "title": "Team meeting", "startHour": 9,  "endHour": 12 }

// Device A moves the start          // Device B moves the end
{ "startHour": 11, "endHour": 12 }      { "startHour": 9, "endHour": 10 }

// Field-level merge
{ "title": "Team meeting", "startHour": 11, "endHour": 10 }  // -1 hour duration

Each edit was valid, but the merged result is not. (“I wish all of my meetings had a -1 duration.”)

Not yet solved

Some data types can’t be merged by picking a winner at all:

  • Counters. Two devices each add a “clap” to 1. Both send 2, but the correct answer is 3.
  • Lists. A adds “Orange”, B adds “Mango”. Replacing the whole list loses one of them.
  • Text. A writes “Hello Amsterdam!”, B writes “Hello! :)”. Neither version is the answer.

Cases like these need the third rail, Collaboration, where you sync intent instead of state.
