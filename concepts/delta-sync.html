Delta Sync

Fetch all relevant data first, then only what changed.

Syncing is hard, so pick the experience first

Before choosing a tool (CloudKit, Firebase, Couchbase, Yjs…) decide what product experience you want. The talk frames it as three rails, each one more powerful and more complex than the last:

Local Read“Show me my data right now”
→
Optimistic UI“Let me act now”
→
Collaboration“Do not lose anyone’s intent”

Local Read is the first rail, and delta sync is how you keep the local store fresh without downloading everything every time.

Initial sync, then deltas

Initial sync

  • Download all relevant data
  • Save a lastUpdate timestamp

Later syncs

  • Send lastUpdate to the server
  • Receive only what changed since then
  • Update lastUpdate
func sync() async throws {
    let since = store.lastUpdate          // nil on first launch → full sync
    let delta = try await api.changes(since: since)

    try store.apply(delta.upserts, deletions: delta.deletedIDs)
    store.lastUpdate = delta.serverTimestamp  // use the server's clock, not the device's
}

When do we trigger the sync?

  • On app open: catch up on what happened while the app was closed.
  • Pull to refresh: the user asks for it explicitly.
  • After each POST / PUT: pick up server-side side effects of your own writes.

These events trigger synchronization; the UI keeps reading from the local store.

Things to consider

  • Initial sync can be really long. Show progress, sync the most important data first and make it resumable.
  • Entities need a versioning mechanism. An updatedAt or version number lets both sides know what changed.
  • You implement on-device logic. Sorting, filtering and search now happen locally, not in the backend query.
  • The backend must support delta sync. That includes reporting deletions (tombstones), not just new and updated rows.
