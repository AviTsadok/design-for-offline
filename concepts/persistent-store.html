The Persistent Store

Why a local, structured store, not a cache, should drive your UI.

Offline is a user-experience decision

When we hear “design for offline” we picture a plane or an elevator. But users expect a polished UI, fast animations and up-to-date information even when they are online. A screen that waits on the network is a slow screen, no matter how fast the CPU or how optimized the Swift code is.

The goal: let people use the app at the speed of touch. The way to get there is to stop rendering screens straight from network responses.

Isn’t that just a cache?

No. A cache and a persistent store solve different problems.

Cache

  • Avoids re-calculations
  • Boosts speed & performance
  • Temporary storage

Persistent Store

  • Structured data storage
  • Query capabilities
  • Supports modifications
  • Long-term retention

The persistent store drives the UI and preserves pending edits.

A cache can be thrown away at any time. A persistent store holds data the user created and hasn’t synced yet, so it has to be modelled, queried and migrated like a real database.

How do we build one?

On iOS you have three common options, all of which map storage onto entities:

  • SQLite: tables you map to entities yourself (or through a library such as GRDB).
  • Core Data: a schema (the model) that generates managed entities.
  • SwiftData: the model is the entity.
import SwiftData

@Model
final class Trip {
    @Attribute(.unique) var id: UUID
    var city: String
    var updatedAt: Date
    var syncState: SyncState   // .synced, .pending, .failed
}

The basic idea is to have everything the user needs on the device, structured and up to date.

Why take on this headache?

  • Consistency. Every screen reads the same data, so an edit on one screen shows up everywhere instead of each endpoint (/trips, /Paris/locations, /alerts) returning its own snapshot.
  • Simplicity. Screens query a local store instead of coordinating many endpoints, loading states and retries.
  • On-device AI. App data, history and device signals sit in one place where on-device models can use them, privately and instantly.
  • Stability. When the backend is unavailable, the app keeps working.
