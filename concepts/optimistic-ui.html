Optimistic UI

Optimistic UI

Update the UI immediately. Confirm with the server later.

Let me act now

The second rail lets users change data without waiting for the network. The UI updates instantly, and the server confirms later.

ReadyUser taps “complete task”
→
PendingUI updates immediately; request in flight
→
ConfirmedServer confirms later
  • A meaningful increase in your app’s independence.
  • Changes happen without waiting for backend confirmation.
  • The assumption is that the backend will approve the changes.
  • Some of the business logic now lives in the client.

Creating content offline is business logic on steroids

Editing an existing item is the easy case. Creating new content offline means the client must do work the backend used to do:

  • Establish relationships. A new contact belongs to a list (Family, Friends, Work) before the server has seen either.
  • Generate unique IDs on the device. You can’t wait for the server to assign one.
  • Validate data. Share the validation rules with the backend (for example as JSON) so both sides agree on what’s valid.
import Foundation

let item = TodoItem(
    id: UUID(),          // client-generated, globally unique
    listID: family.id,     // relationship established locally
    title: "Buy milk",
    syncState: .pending
)
store.insert(item)         // UI updates now
outbox.enqueue(.create(item))  // sent when the network allows

When is Optimistic UI a good fit?

It works well for to-do apps, note-taking, e-commerce and messaging, where:

  • The environment is mostly single-user.
  • The update rate is low.
  • Eventual consistency is acceptable.

The catch: the server can receive an outdated version when two devices edit the same data. That’s where conflict resolution comes in.
